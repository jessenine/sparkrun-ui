# BUG-20260807T162715: Recipes page returns 500 error

## Problem

The `/recipes` page returns HTTP 500 when accessed in a browser.

**Actual behavior**: Navigating to `http://192.168.1.77:5678/recipes` shows "Internal Server Error" (500). Server logs show ENOENT from sparkrun call.

**Expected behavior**: The recipes page should load and display the list of available recipes with their names, models, runtime, and registry.

**How to reproduce**: Navigate to `http://192.168.1.77:5678/recipes` in a browser. Or call `curl -X POST http://192.168.1.77:5678/rpc/recipes/list -H 'Content-Type: application/json' -d '{"json":{"all":true}}'`.

## Root Cause Analysis

**Root cause**: Same as BUG-20260807T162700 — `sparkrun` binary is not available inside the Docker container. The `recipes.list` handler calls `runSparkrunJson(["list", "--all", "--json"])` which spawns `sparkrun` and fails with ENOENT.

**Code path**: `recipes/page.tsx` (SSR) → `serverClient.recipes.list({ all: true })` → `recipes/list.handler` → `runSparkrunJson(["list", "--all", "--json"])` → `runSparkrun()` → `spawn sparkrun` → ENOENT → throw ORPCError → Next.js page crashes with 500.

**Why no fallback exists**: The `list` handler (and all other recipes handlers: `listExtended`, `listWithCategory`, `readYaml`, `show`, `info`, `validate`, `dryRun`) call `runSparkrunJson` directly with no try/catch or fallback. They assume `sparkrun` is always available.

**Security impact**: NONE — no exploit path identified. ENOENT is a missing file, not a security vulnerability.

**Risk level**: High — entire recipes feature is completely broken in deployment.
